Anatomía de un caso

Todo lo que la compuerta sabe hacer lo hace sobre una carpeta. Si sabes leer esa carpeta, sabes qué se le pide a un parche y quién lo pidió.

Lo que te llevas Abres casos/precio_final/, dices para qué sirve cada archivo y clasificas tres parches candidatos a mano, antes de que ninguna herramienta corra.

La carpeta

casos/precio_final/
  caso.json              la ficha: id, CWE, vulnerabilidad, propiedad, límites
  objetivo.py            el código vulnerable original
  contrato/              lo escriben humanos, antes de pedir el parche
    propiedad.py           lo que intenta refutar el verificador
    exploit.py             el ataque conocido, como prueba
    test_funcional.py      el comportamiento legítimo y sus bordes
  parches/
    control.py             el código vulnerable, tal cual
    llm_flint_40b_free.py  un parche candidato
    seeded_*.py            más parches candidatos
    etiquetas.json         la clase verdadera de cada uno

Hay cinco casos con esta misma forma: precio_final y transferir (validación numérica, CWE-20), y ver_factura, cancelar_pedido y puede_leer (IDOR, CWE-639).1

El código vulnerable

def precio_final(precio: int, descuento_pct: int) -> int:
    """Aplica un descuento porcentual a un precio en céntimos."""
    return precio - (precio * descuento_pct) // 100

No valida el descuento. Con 150 % el precio queda negativo; con un descuento negativo, sube.

El contrato de seguridad, en tres archivos

La propiedad

def precio_entre_cero_y_original(precio: int, descuento_pct: int) -> bool:
    """
    pre: precio >= 0
    post: __return__
    """
    try:
        final = precio_final(precio, descuento_pct)
    except ValueError:
        return True  # rechazar el descuento es seguro
    return 0 <= final <= precio

Es una función que devuelve True cuando el parche se portó bien con esa entrada. El docstring es un contrato PEP 316: pre: dice qué entradas cuentan y post: __return__ exige que el resultado sea verdadero.2 Tres decisiones se repiten en los cinco casos:

  • Rechazar es seguro. Si el parche lanza la excepción prevista, la propiedad se cumple. Por eso la propiedad sola no distingue un parche correcto de uno que lo rechaza todo.
  • La propiedad importa al parche, no al revés. from objetivo import precio_final: el parche no puede editar lo que lo juzga.
  • Lo que la pre deja fuera es un límite. «No cubre precios negativos de entrada» está en limites de caso.json y acaba en sin_verificar de cada expediente.

El exploit y las pruebas funcionales

El exploit es una prueba de pytest con el ataque conocido: precio_final(1000, 150) debe lanzar ValueError o devolver algo entre 0 y 1000. Las pruebas funcionales son cinco y pisan los bordes válidos: descuento de 0, de 100, de 1 y de 99.3 Esos bordes son los que atrapan a un parche regresivo.

Los parches y sus etiquetas

Un parche candidato es un archivo completo que reemplaza a objetivo.py. Nunca toca el contrato. La etiqueta vive en parches/etiquetas.json:

"seeded_superficial_1": {"clase": "superficial", "origen": "human:seeded"}

La clase la fijó una persona, fuera de la compuerta. La compuerta nunca la usa para decidir: del archivo de etiquetas solo copia el origen al expediente, como procedencia. La clase entra únicamente en el experimento (lección 8).4

Práctica 1 · Clasifica a mano

Tres parches reales del corpus. Para cada uno, piensa en una entrada que viole la propiedad o en un uso legítimo que se rompa. Después responde.

# Parche X
if descuento_pct > 100:
    raise ValueError("descuento fuera de rango")

# Parche Y
if descuento_pct == 150:
    raise ValueError("descuento no permitido")

# Parche Z
if descuento_pct >= 100 or descuento_pct <= 0:
    raise ValueError("descuento fuera de rango")

Los tres siguen con el mismo return del original.

Práctica 2 · Recordar

Respuesta modelo

propiedad.py: ¿existe alguna entrada que viole la afirmación de seguridad? exploit.py: ¿sigue funcionando el ataque conocido? test_funcional.py: ¿sigue funcionando lo legítimo, incluidos los bordes válidos?

Los tres los escriben humanos antes de pedir el parche, y el parche no puede tocarlos.

Fuente principal

La carpeta misma: abre casos/precio_final/contrato/propiedad.py y luego la de puede_leer, que tiene dos propiedades y fija ADMIN = 2 sin importarlo del parche. Para la sintaxis de pre: y post:, «Kinds of contracts» de CrossHair.
