Usar Patchlayer de punta a punta

Tres subcomandos, tres preguntas distintas. Esta lección se hace con la terminal abierta: cada paso dice qué deberías ver, para que sepas en el acto si lo entendiste.

Lo que te llevas Revisas un parche, lees su expediente, metes un parche tuyo en la compuerta y regeneras el experimento, sabiendo qué archivo escribe cada comando.

Los tres subcomandos

ComandoPreguntaEscribe
patchlayer revisar <caso> <parche>¿Hay evidencia favorable para este parche?expedientes/<caso>/<parche>.json
patchlayer experimento¿Cuántos parches de cada clase acepta cada configuración?un expediente por par, y experimento.json, tabla.md y reporte.html en resultados/
patchlayer mutacion¿La evidencia nota variantes inseguras del parche correcto?resultados/mutacion.json y mutacion.md, y expedientes/mutantes/

Todos se lanzan desde la raíz del repo con uv run. expedientes/ y resultados/ están fuera de git: son salidas que se regeneran.1

Hazlo

  1. Prepara el entorno (Python 3.12 y uv).

    uv sync

  2. Revisa el parche correcto de precio_final. Predice antes el veredicto de C.

    uv run patchlayer revisar precio_final llm_flint_40b_free; echo "código: $?"

    C: evidencia_favorable y código: 0.

  3. Ahora un parche superficial. Predice el veredicto y el código de salida.

    uv run patchlayer revisar precio_final seeded_superficial_1; echo "código: $?"

    C: rechazado y código: 1. El código es 0 solo con evidencia favorable en C; rechazado y no concluyente dan 1. Así es como una CI bloquearía el merge.

  4. Abre el expediente y busca tres cosas: el contraejemplo, la observación y lo que quedó sin verificar.

    uv run python -m json.tool expedientes/precio_final/seeded_superficial_1.json | less

    "contraejemplo": "precio_entre_cero_y_original(1, -1)", una observación que empieza por «B favorable pero C rechaza» y cinco líneas en sin_verificar.

  5. Mete un parche tuyo. Copia el parche correcto, rómpelo a tu gusto y revísalo.

    cp casos/precio_final/parches/llm_flint_40b_free.py casos/precio_final/parches/mio.py
# edita mio.py: cambia «> 100» por «> 101»
uv run patchlayer revisar precio_final mio

    Predice primero qué capas lo notan. Resultado real: funcional pasa, exploit pasa, verificador falla con el contraejemplo precio_entre_cero_y_original(109, 101). A y B dan evidencia favorable y C rechaza. Es el mismo cambio que mutmut hizo en la lección 10. Prueba luego con > 200: ahí ya lo nota el exploit.

  6. Borra tu parche antes de seguir, para no contaminar el corpus.

    rm casos/precio_final/parches/mio.py expedientes/precio_final/mio.json

    Un parche sin entrada en etiquetas.json sí se revisaría en el experimento, pero saldría como «parche sin etiqueta: fuera de la tabla».

  7. Corre el experimento completo.

    uv run patchlayer experimento

    La tabla A/B/C con 15/15, 10/15 y 0/15 en superficiales, las métricas secundarias, y tres archivos en resultados/. Tarda unos 20 segundos. Abre resultados/reporte.html en el navegador.

  8. Corre la mutación.

    uv run patchlayer mutacion

    Cerca de 45 segundos; casi todo es mutmut. Sale el reporte de mutación en pantalla, con «Reporte sin firmar» mientras nadie llene mutantes/firma.json (lección 10). Con --sin-sintacticos no corre mutmut y el reporte que escribe ya no trae esa sección.

Dos cosas que no se hacen por accidente

La corrida oficial vive en evidencia/experimento/ y está versionada. Solo se regenera a propósito, cuando cambia el corpus o la compuerta: uv run patchlayer experimento --salida evidencia/experimento.

Los parches que revisas se ejecutan de verdad en tu máquina, en un subproceso con tiempo límite. No revises código en el que no confías fuera de un entorno aislado: es el tercer límite fijo de todo expediente.

Si tocas el código

Antes de dar un cambio por terminado, los tres controles tienen que salir en 0. Son los mismos que corre la CI en cada PR a main:2

uv run ruff check
uv run basedpyright
uv run pytest -q

Códigos de salida de revisar

CódigoSignifica
0C dio evidencia favorable
1C rechazó o no concluyó
2Uso incorrecto: el parche no existe en casos/<caso>/parches/
